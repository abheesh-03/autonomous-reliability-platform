# Phase 10: AI evaluation and reliability benchmarking

## 1. Why Phase 10 exists

Phases 5-9 built a complete AI-assisted reliability loop: evidence-
grounded investigation (Phase 5), RAG retrieval (Phase 6), durable
LangGraph orchestration (Phase 7), human-approved allowlisted
remediation (Phase 8), and an operator console (Phase 9). Every phase
has its own real-stack acceptance script and unit tests, but none of
them ask the question Phase 10 exists to answer: **given this
platform's own real citation/retrieval/policy logic, can a test
harness independently detect when something that matters — a
fabricated citation, an unsafe remediation decision, a human-approval
bypass — slips through?** A test suite that only ever confirms the
happy path proves nothing about regressions; Phase 10's own existence
test (Gate D) is that it can fail on purpose.

## 2. Deterministic vs. LLM-based evaluation

Two distinct, never-conflated evaluation modes:

- **Deterministic offline** (the default, and the only mode CI ever
  runs): every check calls real, non-stochastic production code
  (`parse_and_validate`, `classify_investigation`,
  `build_prompts`, the real LangGraph node functions) against fixed
  inputs. The exact same input always produces the exact same
  `PASS`/`FAIL`/`NOT_EVALUATED` verdict, forever — this is what makes
  the regression baseline (section 4) meaningful.
- **Real-model** (optional, explicitly opt-in, never required):
  re-runs a bounded citation-check subset against a real, configured
  LLM provider. Its output is stochastic by nature — the harness
  never claims a fixed verdict for it beyond "did this specific real
  response cite only real ids," and its results are reported
  separately from the deterministic safety/quality counts so a flaky
  real-model run can never gate CI or silently inflate a pass rate.

See `evals/README.md` sections 6 and 9 for the full, honest limitation
list of each mode.

## 3. Dataset provenance and versioning

`evals/cases/<version>/*.json`, one file per case, each carrying its
own `dataset_version` (checked against the directory by the loader)
and a `provenance.kind` of `"real_corpus"` (built from a real,
source-controlled file — today, `knowledge/runbooks/*.md`),
`"synthetic"` (hand-constructed to mirror a real contract/shape, never
captured from a live incident), or `"real_fixture"` (reserved for a
future real, anonymized artifact). `evals/datasets/<version>/manifest.json`
records when a version was created and its category breakdown.
**Every synthetic case says so in its own `provenance.notes`** — this
dataset never claims a constructed fixture is observed production
truth.

## 4. Ground-truth labeling strategy

Every case's `expected_outcome` was derived by a human directly from
this platform's own already-documented contract — a function's own
docstring, a module's own stated invariant, a graph node's own policy
constant, or the literal content of a real runbook file —
and `ground_truth_rationale` names that specific rule. **No case's
expected answer was generated by asking an LLM to produce or grade its
own output.** Doing so would make the harness circular: the system
being measured would also be the judge of whether it measured
correctly. This is why `evals/scoring/investigation_quality.py`'s own
rubric check (no `confidence="high"` hypothesis with zero supporting
evidence) is scoped so narrowly — it is only ever applied where this
platform's own existing validation logic already guarantees the
answer, never as a free-standing semantic judgment.

## 5. Production-code reuse (the actual tested seams)

No scoring module reimplements platform logic. Each one imports and
calls the real function directly (editable-installed from the real
service packages):

| Scoring module | Real production code it calls |
|---|---|
| `citation.py` | `investigator_service.llm.prompt.build_prompts`, `investigator_service.llm.provider.StubProvider`, `investigator_service.llm.validation.parse_and_validate` |
| `retrieval.py` | `retrieval_service.knowledge.load_knowledge_documents`, `retrieval_service.chunking.chunk_text`, `retrieval_service.embeddings.provider.LocalLexicalEmbeddingProvider` — over the real `knowledge/runbooks/*.md` corpus |
| `investigation_quality.py` | `agent_runtime_service.graph.nodes.classify_investigation`, `investigator_service.domain.investigation.InvestigationReport` (for real shape validation) |
| `remediation_safety.py` | `agent_runtime_service.graph.build.compile_graph` / `graph.nodes.build_nodes`, with `langgraph.checkpoint.memory.InMemorySaver` and minimal fake control-plane/investigator/tool-gateway doubles (`evals/fakes/doubles.py`) — the same offline seam `agent-runtime-service`'s own `tests/test_remediation_graph.py` already uses |
| `adversarial_deterministic.py` | `investigator_service.llm.prompt.build_prompts` (the same function as `citation.py`, exercised for its escaping/rendering behavior instead of its shown-id output) |
| `real_model.py` (optional) | the above `citation.py` pipeline, with `investigator_service.llm.provider.OpenAIProvider` substituted for `StubProvider` |

**What this harness deliberately does NOT exercise offline**, and why:

- `control-plane`'s own atomic approve/reject transaction
  (`repositories/remediation_repository.py::decide`) requires a real
  PostgreSQL session — already proven by that service's own
  `tests/test_remediation_transactions.py` (a real-database test) and
  by Phase 8/9's own live acceptance scripts. Re-deriving it here
  would mean either standing up a real database (violating this
  phase's own "no privileged production credential, no Docker socket
  for AI scoring" requirement) or re-implementing the transaction
  logic as a second, divergence-prone copy — neither is acceptable.
- `tool-gateway`'s own compiled-in Go allowlist
  (`internal/allowlist/allowlist.go`) is Go, not Python-importable,
  and is proven by its own Go test suite plus Phase 8's real
  acceptance script.

This is a deliberate scope boundary, not an oversight — see
`evals/README.md` section 2 and section 12.

## 6. Metrics and limitations

See `evals/README.md` section 6 for the full per-metric limitation
text (citation validity is exact/deterministic; retrieval metrics use
a deterministic LEXICAL embedding provider, never the real semantic
one production uses; investigation-quality classification is a
three-way label from real orchestration logic, never free-text
hallucination detection; remediation-safety checks are binary
structural safety outcomes, never a semantic judgment).

## 7. Safety invariants

Every case declares `is_hard_safety_invariant`. The following are
treated as HARD — a single failure anywhere fails the whole offline
evaluation (`RunReport.exit_code() != 0`), regardless of how many
other cases pass:

- A fabricated evidence or retrieval-context citation surviving into
  sanitized output (CIT-008, CIT-009, ADV-010).
- A remediation proposal being created for an ineligible incident, or
  without tool-gateway's own independent precondition being met
  (REM-002, REM-011).
- `execute_remediation` being reached for anything other than a
  literal, trusted `{"decision": "approved"}` resume payload —
  including a malformed/attacker-shaped value (REM-012) and a genuine
  rejection (REM-014).

Everything else (investigation-quality classification, retrieval
hit/miss, the one positive-control remediation-success case REM-013)
is a SOFT quality metric — reported, compared against the recorded
baseline, never silently absorbed, but it alone does not fail the run.
No soft metric carries an invented numeric threshold (e.g. "95%
accuracy") — every current soft case is a binary match against a
human-reviewed expectation, and MRR/Hit@k are reported as plain
observed numbers with no pass/fail threshold attached, since this
dataset (2 retrieval cases, a 4-document corpus) is far too small to
justify one.

## 8. Negative-control methodology

`evals/tests/test_*_scoring.py` each include dedicated negative
controls: a case whose `expected_outcome` is DELIBERATELY WRONG (e.g.
"this fabricated citation should survive", "this ineligible incident
should produce a proposal", "this attacker-shaped decision should
execute") and an assertion that the harness reports `FAIL` for it —
proving the harness can actually detect the failure mode it exists to
catch, not merely that the real, correctly-labeled dataset happens to
pass. `evals/tests/test_security_no_mutation.py` additionally proves,
by monkeypatching `httpx`'s own send path to raise, that a full
offline run never opens a real network connection, and that the
real-model mode's own double-gate (`real_model_is_available()`) fails
closed — including the specific case where `INVESTIGATOR_LLM_PROVIDER=stub`
is set (which satisfies the service's own `configured` property
without making any real call) — never letting that be mistaken for a
real invocation.

Prompt-injection testing here is explicitly split in two, per this
phase's own requirement:

1. **Deterministic enforcement** (`adversarial_deterministic.py`,
   ADV-010): proves the real `build_prompts`/`_escape_untrusted`
   boundary renders delimiter-shaped hostile text as inert, escaped
   data with no structurally-injected extra block. This is a fact
   about the RENDERER, provable with certainty, offline.
2. **Actual LLM susceptibility** (the optional real-model mode):
   would require a real model call to say anything meaningful about
   whether a model obeys an embedded instruction — this harness never
   claims (1) as evidence of (2), and real-model mode itself only ever
   checks citation validity, never "did the model obey the
   injection," since that would require a semantic judgment this
   harness does not attempt to automate.

No shell/tool-gateway execution is possible from any evaluation
input: `remediation_safety.py` never imports `psycopg`/
`AsyncPostgresSaver`/any Docker SDK (enforced by its own structural
test), and the one "execution" it ever triggers is a fake, in-process
Python object's own method call (`evals/fakes/doubles.py`), never a
real HTTP call to tool-gateway or any other service.

## 10. Running in CI

`.github/workflows/ci.yml` gained three new steps, placed as the fast
OFFLINE gate immediately after `Build web-console` and before
`Create runtime .env from .env.example` — i.e. strictly before the
expensive Docker/Compose acceptance section begins, per this phase's
own placement requirement. They reuse the SAME Python 3.13 interpreter
and the SAME already-editable-installed investigator-service/
retrieval-service/agent-runtime-service packages the existing
`Install X dependencies`/`Run X tests` steps earlier in the job already
set up — no second install of any of them, no Docker, no database, no
real LLM/embedding API call, no privileged production credential. Only
this harness's own `pytest`/`pytest-asyncio` dev dependency is
installed fresh. Measured added cost: well under one second of actual
evaluation/test runtime, plus a few seconds of `pip install`; the job's
existing `timeout-minutes: 90` was not touched, since this addition is
negligible next to the Docker/Compose acceptance steps it precedes.

## 13. What Phase 10 does NOT prove

See `evals/README.md` section 12 for the full list. In short: real
semantic investigation/retrieval quality, real LLM prompt-injection
resistance, and control-plane/tool-gateway's own real-database/Go
safety enforcement are all explicitly OUT of this harness's offline
scope, proven elsewhere (by those services' own existing tests and
Phase 8/9's live acceptance scripts) or left to the optional,
non-deterministic real-model mode with its own stated limitations.
Passing this harness is necessary evidence of correct deterministic
behavior; it is never claimed as sufficient evidence that the overall
AI system is "good."

## 15. Final independent-review correction pass

An independent review of the uploaded Phase 10 source found four
concrete framework bugs, all fixed in a single focused pass (no
production service touched):

1. **`RunReport.exit_code()` ignored `not_evaluated`.** A required
   case (hard or soft) that could not run produced exit code 0 as long
   as `failed` and `safety_violations` were both empty. Fixed: any
   `not_evaluated > 0` now fails the run, kept strictly separate from
   `safety_violations` (a skipped measurement is never fabricated into
   a detected violation).
2. **`_select_cases()` could silently select zero cases.** An unknown
   `--case-id`/`--category`, or a valid-but-mutually-exclusive
   combination of both, produced an empty case list and a vacuous
   "0 evaluated, exit 0". Fixed: every explicitly requested selector
   is now validated against the loaded dataset before filtering, and
   an empty post-filter selection is its own explicit hard failure.
3. **`evals/datasets/v1/manifest.json` was internally inconsistent**
   (`remediation_safety: 6` when only 5 such cases exist; its own
   `categories` summed to 16 while `total_cases` said 15). Fixed the
   declared count, added an explicit `case_ids` list, and added
   `runner/manifest.py` to validate internal consistency on every run
   and full-dataset completeness (case_ids/categories/total, never
   just a count) on every UNFILTERED run — never on a deliberately
   filtered subset run.
4. **`regression.py` tracked only PASS/FAIL/NOT_EVALUATED outcomes,
   never numeric metrics** — a retrieval ranking could degrade (e.g.
   `reciprocal_rank` 1.0 → 0.5) while `require_hit` stayed satisfied,
   making the regression invisible. Fixed: the `Baseline` schema now
   records each case's own measured `metrics`; `compare_metrics_to_baseline`
   reports any drift (`RunReport.metric_drift`) in both JSON and
   Markdown, kept strictly separate from and never gating `exit_code()`
   (no invented accuracy threshold). Baseline loading is now strict
   for ordinary runs (missing/malformed/wrong-version baseline fails
   outright) and `--update-baseline` only writes when
   `RunReport.is_fully_successful()` is true — an incomplete or failed
   run can never replace the reviewed reference baseline.

38 new regression tests were added across `test_models.py`,
`test_regression.py`, `test_manifest.py` (new file), and
`test_runner_cli.py`, bringing the harness's own test suite to 87
tests. The real, committed dataset (still 15 cases, still 7 hard / 8
soft) was re-validated green end to end after every fix; the
regression baseline was regenerated from a real, fully successful run
(never hand-invented values) and now carries real measured
`reciprocal_rank`/`hit_at_k` figures for the two retrieval cases. See
`evals/README.md` §7, §7a, §7b for the user-facing explanation of each
fix.

## 16. Two further baseline-integrity fixes

A second independent review of this archive found two more concrete
bugs, both fixed without touching production code:

1. **A disappeared baseline metric was silently ignored.**
   `compare_metrics_to_baseline` only ever compared a metric present
   in BOTH the baseline and the current result -- a metric that
   vanished from the current run entirely (not merely changed value)
   was treated as "nothing to compare," never as an incomplete
   measurement. Fixed with a new, separate function,
   `apply_missing_metric_checks`, called in `runner/cli.py` before any
   pass/fail/not_evaluated count is computed: it downgrades the
   affected case to `NOT_EVALUATED` (naming the specific missing
   metric), reusing the existing `exit_code()`/`NOT_EVALUATED`
   machinery rather than introducing a parallel error framework. The
   previously-passing test that asserted the old (wrong) "skipped
   safely" behavior was corrected, not deleted -- it now documents
   that `compare_metrics_to_baseline` itself stays narrowly scoped to
   drift computation, and a new test suite proves the corrected
   completeness behavior.
2. **A filtered run could overwrite the complete baseline.**
   `--update-baseline` accepted any `--case-id`/`--category` filter,
   so a single-case run's own narrow result set could silently replace
   the full, reviewed 15-case baseline. Fixed: `runner/cli.py` now
   rejects `--update-baseline` combined with either filter outright,
   before any file is opened, leaving an existing baseline
   byte-for-byte untouched -- verified directly (file hash compared
   before/after a rejected attempt).

10 new tests were added (`test_regression.py` +5, `test_runner_cli.py`
+5), bringing the harness's own suite to 97 tests. The real,
committed 15-case dataset was re-validated green end to end after
both fixes.
